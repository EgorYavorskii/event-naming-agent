# Регламент разметки фронтовых событий

## 1. Назначение

Регламент задаёт единые правила именования фронтовых событий и передачи дополнительных параметров в аналитическую систему. Он применяется к показам экранов и элементов интерфейса, действиям пользователя, отправке форм, переходам между шагами и результатам операций.

## 2. Базовые принципы

- Одно событие описывает одно конкретное действие или один однозначный факт.
- Имя события отражает бизнес-смысл, а не техническую реализацию компонента.
- Имена событий и строковые значения передаются латиницей. Имена событий пишутся в нижнем регистре.
- Слова разделяются только нижним подчёркиванием. Пробелы, дефисы и кириллица запрещены.
- Схема события согласовывается до разработки и фиксируется в каталоге.
- Существующее имя нельзя использовать для другого смысла.
- В события и dimensions нельзя передавать секретные, платёжные и чувствительные сведения, ФИО, телефон, e-mail, номер карты, номер счёта, ПИН клиента, реквизиты и другие прямые идентификаторы.

## 3. Имя события

Основной шаблон:

`<product>_<screen>_<object>_<action>`

Допустимы сокращённые варианты, когда один элемент не имеет смысла:

- `<product>_<object>_<action>`
- `<product>_<screen>_<action>`

Порядок элементов не меняется.

### Product

Короткий стабильный код продукта или домена. Код выбирается только из утверждённого справочника. Новый код требует согласования с владельцем каталога.

### Screen

Экран или крупный раздел интерфейса. Пишется латиницей в snake_case. Может быть пустым, если событие однозначно описывается через Object.

### Object

Элемент интерфейса или бизнес-сущность. Пишется латиницей в snake_case. Может быть пустым, если событие относится ко всему экрану. Screen и Object одновременно пустыми быть не могут.

### Action

Допустимы только следующие значения:

- `view` — экран или значимый блок фактически показан пользователю;
- `click` — пользователь нажал интерактивный элемент;
- `select` — пользователь выбрал значение или вариант;
- `submit` — пользователь отправил форму или подтвердил ввод;
- `success` — система подтвердила успешное завершение операции;
- `error` — операция завершилась ошибкой;
- `start` — начался отдельный процесс или сценарий;
- `complete` — сценарий или шаг завершён.

Клик, отправка формы и подтверждённый результат являются разными событиями. Одно событие нельзя отправлять одновременно на нажатие и на успешное завершение операции.

## 4. Технические ограничения имени

- Разрешены символы `a-z`, `0-9` и `_`.
- Первый символ — латинская буква.
- Рекомендуемая максимальная длина — 100 символов.
- Запрещены динамические значения: идентификаторы, номера продуктов, даты, суммы, текст пользователя и номера экспериментов.
- Значения фильтров, категорий и вариантов передаются через dimensions, а не через отдельные имена событий.
- Сокращения используются только из утверждённого словаря.

## 5. Trigger

Trigger описывается по-русски в 1–3 предложениях так, чтобы аналитик, разработчик и тестировщик одинаково понимали момент отправки.

- Начинать с субъекта: пользователь или система.
- Указывать точный момент: в момент нажатия, после ответа системы, после фактического показа экрана.
- Для `view` указывать критерий фактического показа. Загрузка данных должна завершиться, пользователю показывается содержимое, а не заглушка.
- Для `success` и `error` указывать, что событие отправляется после ответа системы, а не при нажатии кнопки.
- При необходимости указывать, когда событие не отправляется: повторное нажатие, обновление данных или прерванный сценарий.
- Не использовать технические термины, названия методов, компонентов и API.

## 6. Dimensions

Дополнительные параметры передаются в полях `dimension_1`–`dimension_20`. Для каждого события каталог должен фиксировать соответствие номера dimension и бизнес-параметра. Нельзя назначать номера произвольно.

Формат одной ячейки:

`dimension_1=parameter_name; dimension_2=parameter_name`

Правила:

- элементы разделяются строкой `; ` и идут по возрастанию номера;
- имя параметра пишется латиницей в snake_case;
- `dimension_1`–`dimension_10` предназначены для коротких значений до 100 символов;
- `dimension_11`–`dimension_20` — для длинных контекстных значений до 255 символов;
- смысл, тип, допустимые значения, длина и обязательность параметра фиксируются в каталоге;
- тип значения не меняется от релиза к релизу без согласования;
- отсутствие значения не кодируется строками `-`, `undefined`, `null` или пустой строкой;
- значения нельзя молча обрезать;
- запрещено передавать персональные, секретные и платёжные данные, свободный текст пользователя и прямые идентификаторы;
- не следует дублировать стандартные поля, которые система собирает автоматически;
- нельзя помещать набор параметров в JSON-строку внутри одного dimension без отдельного согласования.

## 7. Проверка по каталогу

Перед созданием новой строки необходимо проверить:

- точное совпадение Event name;
- совпадение смысла на том же экране или объекте;
- существующую схему dimensions;
- утверждённость Product;
- утверждённые значения справочников;
- отсутствие переиспользования старого имени для нового смысла.

Точное или смысловое совпадение помечается как возможный дубль и требует решения человека. Агент не изменяет существующие события самостоятельно.

## 8. Проверка перед результатом

- Имя соответствует шаблону, написано латиницей в нижнем регистре и не содержит запрещённых символов.
- Action выбран из разрешённого списка.
- Screen и Object не пусты одновременно.
- Trigger однозначно описывает момент отправки.
- Клик, отправка формы, успех и ошибка не смешаны.
- Dimensions соответствуют каталогу по номеру, смыслу, типу и длине.
- Нет персональных, секретных и лишних данных.
- Дубликаты и неопределённости вынесены в риски.
- Неподтверждённое поле не получает статус `OK`.

## 9. Формат XLSX

Результат создаётся из встроенного шаблона и содержит листы `Events` и `Риски`.

На листе `Events` используются колонки:

1. `№`
2. `Event name (имя события)`
3. `Product`
4. `Screen`
5. `Object`
6. `Action`
7. `Trigger (когда и почему отправляется)`
8. `Dimensions (одной строкой)`
9. `Проверка`

На листе `Риски` используются смысловые колонки:

1. `№`
2. `Строка БТ`
3. `Тип`
4. `Суть проблемы`
5. `Вариант агента`
6. `У кого уточнить`
7. `Решение аналитика`

Категории риска: `Неоднозначность`, `Неполнота`, `Расхождение с регламентом`, `Возможный дубль`.

Файл всегда является черновиком. Автоматическое значение `OK` не означает согласование человеком.
